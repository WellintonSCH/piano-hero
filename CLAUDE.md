# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Piano Hero**: a Guitar-Hero-style rhythm game that runs entirely in the browser — vanilla JS, no framework, no build tool, no backend. This is the implementation artifact for a TCC (undergraduate thesis, UTFPR); `prompt.md` is the original spec and `relatorio-sistema.md` is a status report documenting the architecture and open research questions — read both for context before making non-trivial changes, since design decisions here are argued in the thesis text, not just the code.

Notes fall toward a hit line; the player plays the right note via real MIDI piano, PC keyboard, or on-screen click/touch. Two modes: **free** (untimed practice queue) and **song** (BPM/tick-timed levels with a hit window, like an actual rhythm game). Song mode supports **chords** (a timeline slot can require more than one simultaneous note) and has two optional toggles: **"Modo espera" (wait mode)** — instead of the note/chord timing out and passing by, the song clock pauses at the pending slot until the player plays it, removing time pressure while keeping the real melody/note order — and **"Demonstração" (demo mode)** — the song auto-plays itself (audio + falling notes + key highlights) at the correct tempo, with player input ignored (shown by a persistent "Demonstração — só observe" badge), so the player can preview a song before attempting it. **End of a song never leaves the player stranded**: when a demo finishes, `checkSongEnd()` waits `DEMO_END_PAUSE_MS` (guarded by `state.demoGen`/`state.song`, so a restart or exit cancels it) and returns to `#screen-song` via `showSongSetup(song, notice)`, whose optional `notice` (`{ text, suggest }`) fills `#setupNotice` and highlights a mode button (`.suggested`, usually Modo espera). The "fase completa" screen always offers Repetir, **Voltar à música** (`#btnBackToSong`) and Fases; after a wait-mode run its primary button is **Agora no ritmo ▶** (`#btnTryNormal`: same song and BPM, wait/demo off) and Próxima fase becomes secondary. The **home screen is a horizontal phase map** (`#screen-home` holds `#levelList.level-map`: numbered bubbles side by side in a zig-zag, joined by an SVG trail redrawn by `drawMapPath()`; swipe or mouse-wheel scrolls it sideways; the first not-yet-completed phase is highlighted and scrolled into view; free mode, the global ranking and a "?" help card are small icon buttons in its corner — no instruction text up front). Tapping a phase opens `#screen-song`, a "how do you want to play" card (Jogar / Modo espera / Demonstração + a BPM speed picker + that phase's own top-5 ranking, stored in `progress.scores[songId]` next to the older single `progress.best`); `playSongAs()` in `main.js` just syncs the same `waitMode`/`demoMode`/`speed` state and ⚙ toggles, it's not a parallel state. The menus live inside `#stage`, so on a phone (short stage) each `.overlay-card` is capped at the stage height and scrolls internally, and the HUD is hidden via CSS `:has()` while a menu card is open. There is **no pause button**: like a video player, tapping/clicking the falling-notes area of the stage (above the keyboard — the keyboard itself still plays notes) pauses, as does Esc. The pause screen is deliberately icon-only, styled like a video player (`.player-controls`: map / −5s / big white ▶ / +5s / back-to-start, inline SVG line icons — never emoji, which render as colored tiles that vary per OS — with `title`/`aria-label` tooltips) over a nearly transparent `#overlay.see-through`, so the frozen notes stay visible; tapping the backdrop also resumes. Dragging the scrubber (or wheel-seeking) **auto-pauses**, so the player can hunt for a spot while seeing the notes there. While seeking, the pause buttons fade out (`#overlay.seeking`, `markSeeking()`) and come back ~0.7 s after the player stops moving, like a video player. **Resuming a song never restarts "cold"**: `resumeGame()` rewinds only the clock by `RESUME_COUNTDOWN` (3 s) — *animated* over `REWIND_ANIM` (`state.rewind`, eased in `updateSong()`), so the notes visibly slide back up like a video rewinding instead of vanishing and popping in at the top — then shows a 3-2-1 (`#countdown`, driven by `state.countdownTo`/`updateCountdown()`), so the upcoming notes fall in from the top again — `cursor`/`targetMidis` stay on the pending note, so earlier notes aren't re-scored. The song start uses the same countdown (`PRE_ROLL` = 3 s). Song mode's speed is picked as **any integer BPM** (slider + ±1 buttons on the song card, `setSetupBpm()`; a range slider in ⚙ Opções, synced by `updateSpeedOptions()`), from `BPM_MIN` up to the song's BPM × `BPM_MAX_FACTOR` — `state.speed` is still the internal multiplier (chosen BPM ÷ `song.bpm`), only the UI is in BPM. The chosen BPM is remembered per song (`progress.prefs.bpm[songId]`). Speed does **not** change points (the old speed bonus was removed); instead each phase keeps **two records** next to its ranking — precision (best %) and speed (highest BPM finished in normal mode with ≥ `SPEED_RECORD_MIN_ACC`%), in `progress.records[songId]` via `updateRecords()` — plus the last attempt (`progress.last[songId]`), all shown on the song card before playing. All options of the last match (hint, effects, mute, wait/demo/metronome, free-mode difficulty, BPM per song) are saved in `localStorage` as they change and restored on load. In wait mode, `resumeGame()` skips the 3 s rewind and 3-2-1 — the pending note waits anyway. A "Silenciar piano" toggle mutes only the piano's own sound output (metronome and timeout cue stay audible) for practicing on a real external instrument while using the PC only as a reference/timer. Opening ⚙ Opções during a song pauses it (`setOptionsOpen()` sets `state.pausedByOptions`), and closing it resumes with the usual rewind + 3-2-1; `showScreen()` clears the flag on any other screen so leaving to the map never auto-resumes. The latency panel (`#latencyPanel`) floats fixed in the bottom-right corner, and the footer (`#feedback`, `#midiRaw`) has a fixed height: anything that changed height above or below the stage moved the desktop keyboard on every note. Secondary settings (hint, effects, mute, latency panel, difficulty/speed, wait/metronome/demo toggles) live behind a collapsible "⚙ Opções" menu in the HUD, not as loose inline controls — keep new settings going into that same panel (`#optionsPanel` in `index.html`) rather than adding more inline HUD clutter. Song navigation is **vertical**: the progress bar is `#vScrub`, a vertical bar on the right edge of the stage spanning only the falling-notes area (start at the bottom, end at the top — the direction notes come from), and dragging the note highway itself up/down (`initHighwayGestures()`: finger down = forward, 1:1 with the fall speed `hitLine / LEAD_TIME`; also works on the see-through pause overlay) seeks; both auto-pause, and a quick tap without movement is still pause/resume. The old horizontal scrub row is hidden via CSS (`#scrubberItem` still exists for the desktop loop lane and still drives visibility); the mouse wheel over the stage also seeks. All of these go through `main.js`'s `seekTo(t)`, the one function that must be used for this (it re-derives `cursor`/`targetMidis` from the new time and clears stale resolved bars) — never set `state.songTime` directly from a new call site. Below the stage, **Repetir trecho** is a row of section buttons (`#sectionChips`, built by `renderSections()`): "Música toda" plus one button per 2/4/8-bar section (`songSections()`: the smallest size giving at most 10 buttons, bar length from `timeSignature` and the current BPM). Clicking one (`selectSection()`) sets `state.loopSection` and the loop markers and jumps there; clicking it again or "Música toda" clears the loop. It replaced an older drag-on-a-thin-lane control (`#loopTrack`, still in the DOM but hidden and unused) that testers found hard to find and use. `state.loopAFrac`/`state.loopBFrac` store the markers as a **fraction (0–1) of `state.songDuration`**, so they survive a speed change. `updateSong()` checks the wraparound and calls `jumpToLoopStart()`: `seekTo(A)` (which resyncs `cursor`/`targetMidis`), then the clock steps back `LOOP_LEAD` (3 s) with a 3-2-1 countdown (`state.countdownTo`) so the section's notes fall in from the top, in every mode; while a loop is on, `syncSongNotes()` doesn't draw slots at or after the section end; `checkSongEnd()` doesn't finish the song while a loop is on. Markers are per-song and get cleared in `startSong()` when a different song loads, but deliberately survive a same-song restart/retry (which only calls `reset()`).

## Running it

There is no build step and no package manager. The app must be served over HTTP — opening `index.html` via `file://` breaks Web MIDI and Web Audio (the page detects this and shows a warning banner).

- Double-click `iniciar.bat` (Windows), or
- `python -m http.server 8000` then open `http://localhost:8000`

No test suite, linter, or formatter is configured. There is no automated test command to run after changes — verify manually in the browser (see below).

## Architecture

Nine script files loaded via plain `<script>` tags in `index.html`, in dependency order:

```
latency.js → research.js → audio.js → notes.js → songs.js → render.js → input.js → gamificacao.js → main.js
```

All modules attach to a single shared global namespace, `window.PianoHero` (aliased `PH` inside each IIFE). Each file is `(function (PH) { 'use strict'; ... })(window.PianoHero)` — there's no module system, so load order in `index.html` matters and must be preserved.

| Module | Responsibility |
|---|---|
| `latency.js` | Input-to-audible-sound latency instrumentation, broken into 4 stages (input→dispatch, dispatch→handler, handler→audio scheduling, scheduling→actual output), using `AudioContext.getOutputTimestamp()` to bridge the `performance.now()` and Web Audio clocks. Export to JSON/CSV via the "Medir latência" panel. |
| `audio.js` | Piano engine: 25 real mp3 samples (Dó3–Dó5, `assets/piano/`), decoded via `decodeAudioData`. Sustain-until-release + exponential-decay tail imitates a real damper. Falls back to a synthesized oscillator if a sample hasn't loaded yet. Notes outside the recorded Dó3–Dó5 range (needed for the wider drawn keyboard, see `notes.js`) play the nearest real sample pitch-shifted via `playbackRate`, but only up to `MAX_SHIFT_SEMITONES` (1 octave) — past that the resampled sample sounds too artificial, so it falls back to the synth oscillator instead, which sounds cleaner than an over-stretched sample. Deliberately has no synthesized "hit" sound layered on top — the piano note itself *is* the hit/miss feedback. A separate `instrumentGain` bus (vs. the metronome/timeout `master` bus) backs the "Silenciar piano" mute toggle. |
| `notes.js` | MIDI↔note-name conversion. The **drawn keyboard** (`WHITE`/`BLACK`, exported `MIN_MIDI`/`MAX_MIDI`) spans 5 octaves (Dó2–Dó7) generated from a range constant, wide enough for songs with a spread-out melody+bass — `input.js`'s MIDI `fold()` reanchors into this same wider range. Free mode's 3 difficulty pools (white keys / C-major scale / with sharps) stay scoped to the original, narrower core range (Dó3–Dó5) independently of the drawn keyboard, via a separate internal `CORE_MIN`/`CORE_MAX` filter — free mode's difficulty is unchanged by how wide the keyboard is drawn. On phones (`COMPACT`: coarse pointer + smaller screen side < 600px, decided once at load; `?oitavas=1`/`?oitavas=5` in the URL forces either; sets `html.compact` for CSS) the game is meant to be **played in landscape** — portrait shows only a "Gire o celular" prompt (`#rotateHint`), and landscape pins `#app` with `position: fixed` (the page can't scroll the game up) and floats the HUD *over* the top of the highway (absolute, transparent gradient, `pointer-events: none` except its buttons; only score/combo + icon buttons — accuracy and song title are hidden during play) so the highway and keyboard get the full screen height, the stage sized to the space actually left on screen (`visualViewport.height` minus the stage's own top, re-measured by `render.js`'s `fitCheck()` — throttled to ~4x/s from the main loop, immediate when a menu opens/closes — the HUD shows/hides between menu and game and Safari's toolbar comes and goes, so a fixed offset cut the keyboard off at the bottom; the page itself never scrolls on phones), and **no scrubber at all** (it sat right under the keys and got bumped while playing — phones navigate with the ⏪/⏩ `SEEK_STEP` buttons in the HUD and on the pause screen, via `seekBy()`, which pauses like the scrubber does; Reiniciar/Menu also leave the HUD since the pause screen has them); `main.js`'s `initFullscreen()` enters Fullscreen API + `screen.orientation.lock('landscape')` on the first tap of the page (once) and via the ⛶ button on the map — iPhone Safari has no page Fullscreen API, so there it's installing via "Adicionar à Tela de Início" (`manifest.webmanifest` with `display: fullscreen` + `apple-mobile-web-app-*` metas; icons in `assets/icons/`, generated by `tools/make_icons.py`) — and the drawn keyboard shrinks to **one octave (Dó4–Dó5)**. Phases that fit that octave whole are listed first and play normally (`availableSongs()` / `PH.notes.songFits()`, which always checks the *default* range); wider pieces come after them as dashed "tocar junto" bubbles (`listenOnly()`), demo-only (no points, Jogar/Modo espera/ranking hidden, demo forced on), with the drawn keyboard widened just for that song to its whole C-to-C octaves via `PH.notes.songRange()`/`setRange()` + `PH.render.relayout()` (`setKeyboardFor()` in `main.js`; any other song or free mode calls `resetRange()`) — rather than crushing wide pieces into one octave; `songs.js` has phone-sized songs written for this range (Hänschen Klein, Seu Lobato, When the Saints, Brahms' lullaby). `buildTimeline()` transposes a whole song by octaves via `PH.notes.songShift()` (0 on desktop), with per-note `fitMidi()` only as a last resort. `input.js` cancels `touchstart` on the canvas — the only thing that stops iOS Safari's long-press text-selection loupe/zoom on a held key — so tap-to-pause listens to `pointerdown`/`pointerup`, not `click` (iOS stops synthesizing clicks there); pointer input is tracked per `pointerId`, so two-finger chords work. In compact mode `render.js` labels white keys with note names instead of PC-keyboard letters. |
| `songs.js` | **Built-in** song data (public-domain melodies), hand-composed. Timing is stored as **integer ticks (PPQ 480)**, like a MIDI file/DAW, converted to seconds only once at timeline build — this avoids accumulated floating-point rounding error across long note sequences. Preserve this tick-based representation when editing or adding songs. Each song is written once as a `notes`/`durations` phrase and lengthened with the local `repeat()` helper (e.g. `repeat(phrase, durations, 2)`) rather than by duplicating arrays by hand — bump the repeat count (or extend the base phrase) to make a song longer. A `notes[i]` entry can be a single MIDI number or an **array of MIDI numbers** (a chord — all pressed together). After defining the built-in `SONGS`, this file also `fetch()`es `songs/manifest.json` and, for each filename listed there, `songs/<file>.json`, pushing each into `PH.songs` asynchronously — that's the mechanism for **custom/imported songs** (see below), kept out of this hand-written file on purpose. |
| `songs/*.json` + `songs/manifest.json` | **Custom/imported** songs (none at the moment: the six complex imported pieces and the `XML/` sources were removed on 2026-11-12 as too hard for beginners and with unchecked arrangement rights; `manifest.json` is `[]`), one JSON file per song, in the same shape as a `songs.js` entry (`id`/`title`/`subtitle`/`bpm`/`timeSignature`/`notes`/`durations`) plus an optional `sustainDurations` array (ticks, parallel to `durations` — see the `buildTimeline()` comment in `main.js` for why this exists). `manifest.json` is a flat JSON array of filenames to load; add a song by dropping its `.json` here and listing the filename, no code changes needed. Generate one from a MusicXML/`.mxl` file with `tools/mxl_to_song.py` (stdlib-only Python, run `--list-voices` first to see what's in the file, then convert with `--voices` picking which ones to merge into chords) rather than hand-writing note arrays for an imported piece. |
| `render.js` | Canvas 2D rendering: DPI-aware sizing, keyboard geometry computed from layout constants, falling note bars (length ∝ note duration), particle/ring hit-feedback effects. In song mode, multiple falling bars can share one timeline slot (a chord) — `state.targetMidis` (not a single `state.target`) is the source of truth for which key(s) are currently expected, used both for the on-screen hint ring and for which bar(s) get the "current target" glow. |
| `input.js` | Unifies three heterogeneous input sources — Web MIDI (`requestMIDIAccess`, raw note-on/off status-byte parsing), PC keyboard (fixed key→MIDI map, two octaves, anti-repeat), and pointer/touch on the drawn keyboard — into two canonical `CustomEvent`s dispatched on `window`: `notePlayed` and `noteReleased`. This input-unification layer is the part of the system the thesis treats as most novel/citable; keep new input sources going through this same event pair rather than talking to game state directly. `fold()` reanchors any MIDI note outside `notes.js`'s drawn-keyboard range into its lowest octave, so an out-of-range physical MIDI keyboard degrades instead of being silently dropped. |
| `main.js` | Game state, orchestration, and the `requestAnimationFrame` loop. Owns the `free`/`song` mode split, timeline building from `songs.js` tick data (a timeline slot's `midis` array has one entry for a plain note, more for a chord — resolved incrementally, one key press at a time, via `state.targetMidis`), hit-window scoring, pause/resume, demo auto-play, `localStorage` progress persistence, and the post-song performance report (early/late tendency, most-missed notes — collapsed behind a "Ver detalhes" toggle under a one-line summary, so the end screen fits a landscape phone). |

### Key timing subtlety

`main.js`'s loop computes two deltas per frame: `dt` (capped at 0.05s, used for particles/visual echoes so a stalled frame doesn't teleport an effect) and `rawDt` (uncapped, used to advance the song's musical clock, `state.songTime`). If `rawDt` were capped too, a dropped frame (background tab, OS hiccup) would make the game think less time passed than actually did, corrupting rhythm timing. `checkAutoMiss()` is written to absorb a large single-frame jump by walking past multiple missed notes at once — don't reintroduce a cap on the clock-advancing delta.

When `state.waitMode` is on, `updateSong()` additionally clamps `state.songTime` so it never advances past the currently-pending note's timestamp (`state.timeline[state.cursor].time`) — that's the whole mechanism behind "the note waits instead of passing by": `checkAutoMiss()`'s timeout condition simply never becomes true while the clock is pinned. `onSongNote()` then accepts the pending note regardless of `dt` in wait mode (no `HIT_WINDOW`/`PERFECT_WINDOW` check, no "perfect" bonus), and the post-song report skips the timing-tendency text since there's no delta data to summarize.

`state.targetMidis` (not a single `state.target`) is the one source of truth for "what note(s) are due right now" — it drives both scoring (`onSongNote`/`checkAutoMiss`) and rendering (`render.js`'s hint ring and "current" bar glow). Any code path that advances `state.cursor` in song mode **must** also resync `state.targetMidis` to `timeline[state.cursor].midis.slice()` (or `[]` past the end) in the same place — `onSongNote()` and `checkAutoMiss()` already do this, and so does demo mode's `advanceDemo()`. Forgetting this in a new code path is a real bug that already happened once: demo mode's auto-advance moved `state.cursor` forward every frame but left `state.targetMidis` pinned to the very first chord, so the rendered "current" note position silently went stale (looked like notes appearing in the wrong place) while the audio (driven straight from `timeline[cursor]`, not from `state.targetMidis`) played correctly — a state/render desync, not an audio bug, even though it manifested as "the song sounds wrong."

### Removed: fingering and one-hand practice

`fingering.js` (per-note hand/finger, read from a `fingers` array or guessed by a heuristic), `tools/add_fingers.js`, the one-hand practice mode (the other hand auto-playing) and the per-hand report were removed: the suggested fingering wasn't reliable. Timeline slots carry only `midis`/`time`/`dur`/`sustain`/`index`; `mxl_to_song.py` no longer writes `fingers`. Don't reintroduce hand data without a reliable source.

### Falling bar length

In song mode a bar is `barLen()`: the note's duration, cut `BAR_GAP` px before the next slot, never under `MIN_BAR`. The old minimum (30 px) and no gap made fast repeated notes overlap and look like one note. `syncSongNotes()` caps slots at `SONG_MAX_SLOTS`, not the free-mode `VISIBLE_NOTES` (7), which hid notes in fast passages.

### Hit window and late presses

Normal mode judges a press against the pending slot with an asymmetric window: late up to `HIT_WINDOW` (0.25 s), early up to `earlyWindow()` = min(`HIT_WINDOW`, half the gap since the previous slot), perfect within `PERFECT_WINDOW` (0.08 s). The early cap is a nearest-onset rule: a press closer to the previous note than to this one is never credited here. When `checkAutoMiss()` expires a slot it stores `state.lastExpired`; a press of one of its still-pending keys within 2 × `HIT_WINDOW` is logged as `late` ("Atrasou!") instead of counting a second miss. The old ±0.35/±0.12 window was measured as too lenient (thesis cases CT11/CT12).

### Research mode and test hooks

`research.js` is inert unless the URL has `?pesquisa=<code>`: then it records one attempt per `reset()` in song mode (`PH.research.attemptStart`/`attemptEnd`, called from `main.js`), clears `pianoHeroProgress` when the participant code changes, and draws its own badge/panel (outside the HUD, which is hidden on the map). `?debug` exposes `PH.debugState = state` for the Puppeteer scripts in `tools/testes/` and turns on the raw MIDI console log in `input.js`.

### First steps (guided intro)

The intro draws **only the middle octave** (`LESSON_MIN`–`LESSON_MAX`, Dó4–Dó5, via `PH.notes.setRange()`; `exitLesson()` resets it), labels the white keys with note names and falls slower (`LESSON_FALL_SPEED`). `render.js` always marks middle C (`middleCMark()`: a dot, plus "Dó central" when the key is wide enough).

`startLesson()` in `main.js` runs a 7-step keyboard intro (black-key groups, all Cs, C-D-E, F-G, A-B, the whole octave, a random challenge over the 7 white notes) ("Primeiros passos", bubble 0 on the map, before phase 1) on top of free-mode mechanics: `state.lesson` holds the step, `fill()` pulls notes from `lessonSource` (the step's fixed queue, or a random draw for the last step) instead of `sequence`, and `onFreeNote()` hands off to `onLessonNote()`, which accepts the target **in any octave** (pitch class). `lessonSyncTarget()` lights every octave of the note on step 1; the banner (`#lessonBanner`) shows the instruction and, after a miss, where that key sits relative to the black-key groups. Hint follows each step's `hint` flag and turns on after two misses in a row; the user's own hint preference is saved and restored by `exitLesson()` (called from `showHome`, `startFree`, `startSong` and the lesson end). `render.js` fills the hinted key while `st.lesson` is set. Completion goes to `progress.intro`; with research mode on, the whole intro is one attempt (`modo = introducao`) with per-step times.

### Gamification and profile

`gamificacao.js` (`PH.gami`) holds only pure functions over `progress`: `starsFor()` (normal mode: ≥95% 3★, ≥80% 2★, ≥50% 1★; wait mode always 1★), `recordAttempt()` (called from `finishSong()`, never for demos: updates `progress.stars`, `attempts`, the day `streak` and returns new medals), `recordTutorial()` (end of the guided song) and `summary()`. Eight medals in `MEDALS`; keep the set small and practice-focused (no coins, lives or shop). `main.js` draws it: stars on map bubbles and the complete screen, a status chip on the map (`#homeStatus`: days in a row + total stars), medal toasts (`#toast`), and `#screen-profile` (name, accent color, dark/light theme, stats, medal grid). Theme/accent are `html[data-theme]`/`html[data-accent]` CSS overrides plus `PH.render.setPalette()` for the canvas (highway background, lanes, note color), applied by `applyLook()` on load and on change. `input.js` ignores keydown while typing in a text field, otherwise letters become piano notes.

### Guided first song (part 2 of the intro)

After the keyboard intro, `startGuide()` runs Hot Cross Buns (`availableSongs()[0]`) in three steps, each preceded by a card (`#screen-guide`, `GUIDE_STEPS`, `showGuide()`): demo → wait mode → normal mode at `GUIDE_SLOW_BPM`, then a card presenting the game's functions. While `state.guide` is set, the demo end (`checkSongEnd`) and `finishSong()` show the next guide card instead of the song screen / complete screen. `showHome`, `startFree`, `startLesson` and `showSongSetup` clear it. Completion is `progress.guide`; map bubble 0 counts as done only with both parts, and resumes the guide if only it is missing (`onIntroBubble()`).

### Mobile performance

The `requestAnimationFrame` loop **skips `update()` and `draw()` entirely while a menu card covers the stage** (map, song setup, help, ranking, song-complete — not pause, where the frozen notes stay visible and move while seeking); `lastTime` keeps advancing so no giant `dt` lands when the menu closes. On phones the canvas DPR is capped at 2, the overlay has no `backdrop-filter`, the current-phase pulse animates a `::after` ring's transform/opacity instead of `box-shadow`, and `updateScrubber()` only touches the DOM when a visible value changes — each of these was measurable jank on a phone. `audio.js` resumes a suspended/`interrupted` AudioContext on any `pointerdown`/`touchend`/`click` (capture phase) and on `visibilitychange`, since iOS interrupts audio after screen lock, app switches, or heavy stalls.

### Communication pattern

Modules don't call into each other's game state directly for input. `input.js` emits `notePlayed`/`noteReleased` on `window`; `main.js` is the only listener and drives both `audio.js` (playback) and its own scoring/state from there. Keep this one-way event flow when adding features — don't have `render.js` or `input.js` reach into `main.js` state, and don't have new input sources bypass the `notePlayed`/`noteReleased` contract.

### Graceful degradation (by design, don't remove)

- No MIDI device → keyboard/mouse still work.
- Sample not yet decoded → synthesized oscillator fallback in `audio.js`.
- Opened via `file://` → explicit warning banner instead of silently broken audio/MIDI.
