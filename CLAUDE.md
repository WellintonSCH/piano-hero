# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Piano Hero**: a Guitar-Hero-style rhythm game that runs entirely in the browser — vanilla JS, no framework, no build tool, no backend. This is the implementation artifact for a TCC (undergraduate thesis, UTFPR); `prompt.md` is the original spec and `relatorio-sistema.md` is a status report documenting the architecture and open research questions — read both for context before making non-trivial changes, since design decisions here are argued in the thesis text, not just the code.

Notes fall toward a hit line; the player plays the right note via real MIDI piano, PC keyboard, or on-screen click/touch. Two modes: **free** (untimed practice queue) and **song** (BPM/tick-timed levels with a hit window, like an actual rhythm game). Song mode supports **chords** (a timeline slot can require more than one simultaneous note) and has two optional toggles: **"Modo espera" (wait mode)** — instead of the note/chord timing out and passing by, the song clock pauses at the pending slot until the player plays it, removing time pressure while keeping the real melody/note order — and **"Demonstração" (demo mode)** — the song auto-plays itself (audio + falling notes + key highlights) at the correct tempo, with player input ignored (shown by a persistent "Demonstração — só observe" badge), so the player can preview a song before attempting it. The **home screen is a horizontal phase map** (`#screen-home` holds `#levelList.level-map`: numbered bubbles side by side in a zig-zag, joined by an SVG trail redrawn by `drawMapPath()`; swipe or mouse-wheel scrolls it sideways; the first not-yet-completed phase is highlighted and scrolled into view; free mode, the global ranking and a "?" help card are small icon buttons in its corner — no instruction text up front). Tapping a phase opens `#screen-song`, a "how do you want to play" card (Jogar / Modo espera / Demonstração + a BPM speed picker + that phase's own top-5 ranking, stored in `progress.scores[songId]` next to the older single `progress.best`); `playSongAs()` in `main.js` just syncs the same `waitMode`/`demoMode`/`speed` state and ⚙ toggles, it's not a parallel state. The menus live inside `#stage`, so on a phone (short stage) each `.overlay-card` is capped at the stage height and scrolls internally, and the HUD is hidden via CSS `:has()` while a menu card is open. There is **no pause button**: like a video player, tapping/clicking the falling-notes area of the stage (above the keyboard — the keyboard itself still plays notes) pauses, as does Esc. The pause screen is deliberately icon-only (🗺️ back to phases / ▶ / ↺, just `title`/`aria-label` tooltips) over a nearly transparent `#overlay.see-through`, so the frozen notes stay visible; tapping the backdrop also resumes. Dragging the scrubber (or wheel-seeking) **auto-pauses**, so the player can hunt for a spot while seeing the notes there. **Resuming a song never restarts "cold"**: `resumeGame()` rewinds only the clock by `RESUME_COUNTDOWN` (3 s) and shows a 3-2-1 (`#countdown`, driven by `state.countdownTo`/`updateCountdown()`), so the upcoming notes fall in from the top again — `cursor`/`targetMidis` stay on the pending note, so earlier notes aren't re-scored. The song start uses the same countdown (`PRE_ROLL` = 3 s). Song mode's speed selector shows actual BPM (computed per-song from `state.song.bpm`, via `updateSpeedOptions()`), not a bare percentage — `state.speed` is still an internal multiplier (0.5–1.5), only the displayed label changed. A "Silenciar piano" toggle mutes only the piano's own sound output (metronome and timeout cue stay audible) for practicing on a real external instrument while using the PC only as a reference/timer. Secondary settings (hint, effects, mute, latency panel, difficulty/speed, wait/metronome/demo toggles) live behind a collapsible "⚙ Opções" menu in the HUD, not as loose inline controls — keep new settings going into that same panel (`#optionsPanel` in `index.html`) rather than adding more inline HUD clutter. Song navigation is **vertical**: the progress bar is `#vScrub`, a vertical bar on the right edge of the stage spanning only the falling-notes area (start at the bottom, end at the top — the direction notes come from), and dragging the note highway itself up/down (`initHighwayGestures()`: finger down = forward, 1:1 with the fall speed `hitLine / LEAD_TIME`; also works on the see-through pause overlay) seeks; both auto-pause, and a quick tap without movement is still pause/resume. The old horizontal scrub row is hidden via CSS (`#scrubberItem` still exists for the desktop loop lane and still drives visibility); the mouse wheel over the stage also seeks. All of these go through `main.js`'s `seekTo(t)`, the one function that must be used for this (it re-derives `cursor`/`targetMidis` from the new time and clears stale resolved bars) — never set `state.songTime` directly from a new call site. Below the scrubber, a dedicated thin lane (`#loopTrack`) is a **loop-practice** control: dragging on empty space draws a new start/end selection in one gesture (`#loopRange`, with `#loopHandleA`/`#loopHandleB` to resize either end afterwards, or drag the middle of the range to move the whole thing) — it's a separate lane specifically so this drag never competes with the main scrubber's drag-to-seek gesture. `state.loopAFrac`/`state.loopBFrac` store the markers as a **fraction (0–1) of `state.songDuration`**, not absolute seconds, specifically so they survive a speed change (which rebuilds the whole timeline with a different `songDuration` via `reset()`) — the same musical position stays the same fraction regardless of tempo. `updateSong()` checks the wraparound and, like the scrubber, jumps back via `seekTo()` rather than touching `state.songTime` directly. Markers are per-song and get cleared in `startSong()` when a different song loads, but deliberately survive a same-song restart/retry (which only calls `reset()`).

## Running it

There is no build step and no package manager. The app must be served over HTTP — opening `index.html` via `file://` breaks Web MIDI and Web Audio (the page detects this and shows a warning banner).

- Double-click `iniciar.bat` (Windows), or
- `python -m http.server 8000` then open `http://localhost:8000`

No test suite, linter, or formatter is configured. There is no automated test command to run after changes — verify manually in the browser (see below).

## Architecture

Six script files loaded via plain `<script>` tags in `index.html`, in dependency order:

```
latency.js → audio.js → notes.js → songs.js → render.js → input.js → main.js
```

All modules attach to a single shared global namespace, `window.PianoHero` (aliased `PH` inside each IIFE). Each file is `(function (PH) { 'use strict'; ... })(window.PianoHero)` — there's no module system, so load order in `index.html` matters and must be preserved.

| Module | Responsibility |
|---|---|
| `latency.js` | Input-to-audible-sound latency instrumentation, broken into 4 stages (input→dispatch, dispatch→handler, handler→audio scheduling, scheduling→actual output), using `AudioContext.getOutputTimestamp()` to bridge the `performance.now()` and Web Audio clocks. Export to JSON/CSV via the "Medir latência" panel. |
| `audio.js` | Piano engine: 25 real mp3 samples (Dó3–Dó5, `assets/piano/`), decoded via `decodeAudioData`. Sustain-until-release + exponential-decay tail imitates a real damper. Falls back to a synthesized oscillator if a sample hasn't loaded yet. Notes outside the recorded Dó3–Dó5 range (needed for the wider drawn keyboard, see `notes.js`) play the nearest real sample pitch-shifted via `playbackRate`, but only up to `MAX_SHIFT_SEMITONES` (1 octave) — past that the resampled sample sounds too artificial, so it falls back to the synth oscillator instead, which sounds cleaner than an over-stretched sample. Deliberately has no synthesized "hit" sound layered on top — the piano note itself *is* the hit/miss feedback. A separate `instrumentGain` bus (vs. the metronome/timeout `master` bus) backs the "Silenciar piano" mute toggle. |
| `notes.js` | MIDI↔note-name conversion. The **drawn keyboard** (`WHITE`/`BLACK`, exported `MIN_MIDI`/`MAX_MIDI`) spans 5 octaves (Dó2–Dó7) generated from a range constant, wide enough for real songs with a spread-out melody+bass (see `canonfull` in `songs.js`) — `input.js`'s MIDI `fold()` reanchors into this same wider range. Free mode's 3 difficulty pools (white keys / C-major scale / with sharps) stay scoped to the original, narrower core range (Dó3–Dó5) independently of the drawn keyboard, via a separate internal `CORE_MIN`/`CORE_MAX` filter — free mode's difficulty is unchanged by how wide the keyboard is drawn. On phones (`COMPACT`: coarse pointer + smaller screen side < 600px, decided once at load; `?oitavas=1`/`?oitavas=5` in the URL forces either; sets `html.compact` for CSS) the game is meant to be **played in landscape** — portrait shows only a "Gire o celular" prompt (`#rotateHint`), and landscape gets a one-line HUD, the stage sized to the space actually left on screen (`visualViewport.height` minus the stage's own top, re-measured every frame by `render.js`'s `fitCheck()` — the HUD shows/hides between menu and game and Safari's toolbar comes and goes, so a fixed offset cut the keyboard off at the bottom; the page itself never scrolls on phones), and **no scrubber at all** (it sat right under the keys and got bumped while playing — phones navigate with the ⏪/⏩ `SEEK_STEP` buttons in the HUD and on the pause screen, via `seekBy()`, which pauses like the scrubber does; Reiniciar/Menu also leave the HUD since the pause screen has them); `main.js`'s `initFullscreen()` enters Fullscreen API + `screen.orientation.lock('landscape')` on the first tap of the page (once) and via the ⛶ button on the map — iPhone Safari has no page Fullscreen API, so there it's installing via "Adicionar à Tela de Início" (`manifest.webmanifest` with `display: fullscreen` + `apple-mobile-web-app-*` metas; icons in `assets/icons/`, generated by `tools/make_icons.py`) — and the drawn keyboard shrinks to **one octave (Dó4–Dó5)**. Only phases that fit that octave whole are listed on the phone (`availableSongs()` filters by `PH.notes.songFits()`), rather than crushing wide pieces into it; `songs.js` has phone-sized songs written for this range (Hänschen Klein, Seu Lobato, When the Saints, Brahms' lullaby). `buildTimeline()` transposes a whole song by octaves via `PH.notes.songShift()` (0 on desktop), with per-note `fitMidi()` only as a last resort. `input.js` cancels `touchstart` on the canvas — the only thing that stops iOS Safari's long-press text-selection loupe/zoom on a held key — so tap-to-pause listens to `pointerdown`/`pointerup`, not `click` (iOS stops synthesizing clicks there); pointer input is tracked per `pointerId`, so two-finger chords work. In compact mode `render.js` labels white keys with note names instead of PC-keyboard letters. |
| `songs.js` | **Built-in** song data (public-domain melodies), hand-composed. Timing is stored as **integer ticks (PPQ 480)**, like a MIDI file/DAW, converted to seconds only once at timeline build — this avoids accumulated floating-point rounding error across long note sequences. Preserve this tick-based representation when editing or adding songs. Each song is written once as a `notes`/`durations` phrase and lengthened with the local `repeat()` helper (e.g. `repeat(phrase, durations, 2)`) rather than by duplicating arrays by hand — bump the repeat count (or extend the base phrase) to make a song longer. A `notes[i]` entry can be a single MIDI number or an **array of MIDI numbers** (a chord — all pressed together). After defining the built-in `SONGS`, this file also `fetch()`es `songs/manifest.json` and, for each filename listed there, `songs/<file>.json`, pushing each into `PH.songs` asynchronously — that's the mechanism for **custom/imported songs** (see below), kept out of this hand-written file on purpose. |
| `songs/*.json` + `songs/manifest.json` | **Custom/imported** songs, one JSON file per song, in the same shape as a `songs.js` entry (`id`/`title`/`subtitle`/`bpm`/`timeSignature`/`notes`/`durations`) plus an optional `sustainDurations` array (ticks, parallel to `durations` — see the `buildTimeline()` comment in `main.js` for why this exists). `manifest.json` is a flat JSON array of filenames to load; add a song by dropping its `.json` here and listing the filename, no code changes needed. Generate one from a MusicXML/`.mxl` file with `tools/mxl_to_song.py` (stdlib-only Python, run `--list-voices` first to see what's in the file, then convert with `--voices` picking which ones to merge into chords) rather than hand-writing note arrays for an imported piece. |
| `render.js` | Canvas 2D rendering: DPI-aware sizing, keyboard geometry computed from layout constants, falling note bars (length ∝ note duration), particle/ring hit-feedback effects. In song mode, multiple falling bars can share one timeline slot (a chord) — `state.targetMidis` (not a single `state.target`) is the source of truth for which key(s) are currently expected, used both for the on-screen hint ring and for which bar(s) get the "current target" glow. |
| `input.js` | Unifies three heterogeneous input sources — Web MIDI (`requestMIDIAccess`, raw note-on/off status-byte parsing), PC keyboard (fixed key→MIDI map, two octaves, anti-repeat), and pointer/touch on the drawn keyboard — into two canonical `CustomEvent`s dispatched on `window`: `notePlayed` and `noteReleased`. This input-unification layer is the part of the system the thesis treats as most novel/citable; keep new input sources going through this same event pair rather than talking to game state directly. `fold()` reanchors any MIDI note outside `notes.js`'s drawn-keyboard range into its lowest octave, so an out-of-range physical MIDI keyboard degrades instead of being silently dropped. |
| `main.js` | Game state, orchestration, and the `requestAnimationFrame` loop. Owns the `free`/`song` mode split, timeline building from `songs.js` tick data (a timeline slot's `midis` array has one entry for a plain note, more for a chord — resolved incrementally, one key press at a time, via `state.targetMidis`), hit-window scoring, pause/resume, demo auto-play, `localStorage` progress persistence, and the post-song performance report (early/late tendency, most-missed notes). |

### Key timing subtlety

`main.js`'s loop computes two deltas per frame: `dt` (capped at 0.05s, used for particles/visual echoes so a stalled frame doesn't teleport an effect) and `rawDt` (uncapped, used to advance the song's musical clock, `state.songTime`). If `rawDt` were capped too, a dropped frame (background tab, OS hiccup) would make the game think less time passed than actually did, corrupting rhythm timing. `checkAutoMiss()` is written to absorb a large single-frame jump by walking past multiple missed notes at once — don't reintroduce a cap on the clock-advancing delta.

When `state.waitMode` is on, `updateSong()` additionally clamps `state.songTime` so it never advances past the currently-pending note's timestamp (`state.timeline[state.cursor].time`) — that's the whole mechanism behind "the note waits instead of passing by": `checkAutoMiss()`'s timeout condition simply never becomes true while the clock is pinned. `onSongNote()` then accepts the pending note regardless of `dt` in wait mode (no `HIT_WINDOW`/`PERFECT_WINDOW` check, no "perfect" bonus), and the post-song report skips the timing-tendency text since there's no delta data to summarize.

`state.targetMidis` (not a single `state.target`) is the one source of truth for "what note(s) are due right now" — it drives both scoring (`onSongNote`/`checkAutoMiss`) and rendering (`render.js`'s hint ring and "current" bar glow). Any code path that advances `state.cursor` in song mode **must** also resync `state.targetMidis` to `timeline[state.cursor].midis.slice()` (or `[]` past the end) in the same place — `onSongNote()` and `checkAutoMiss()` already do this, and so does demo mode's `advanceDemo()`. Forgetting this in a new code path is a real bug that already happened once: demo mode's auto-advance moved `state.cursor` forward every frame but left `state.targetMidis` pinned to the very first chord, so the rendered "current" note position silently went stale (looked like notes appearing in the wrong place) while the audio (driven straight from `timeline[cursor]`, not from `state.targetMidis`) played correctly — a state/render desync, not an audio bug, even though it manifested as "the song sounds wrong."

### Communication pattern

Modules don't call into each other's game state directly for input. `input.js` emits `notePlayed`/`noteReleased` on `window`; `main.js` is the only listener and drives both `audio.js` (playback) and its own scoring/state from there. Keep this one-way event flow when adding features — don't have `render.js` or `input.js` reach into `main.js` state, and don't have new input sources bypass the `notePlayed`/`noteReleased` contract.

### Graceful degradation (by design, don't remove)

- No MIDI device → keyboard/mouse still work.
- Sample not yet decoded → synthesized oscillator fallback in `audio.js`.
- Opened via `file://` → explicit warning banner instead of silently broken audio/MIDI.
